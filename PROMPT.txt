上周一个在换热器厂做技术支持的朋友吐槽：同一台管壳式换热器，销售用效能—传热单元数法报出来的热负荷是 412 kW，工艺部门用对数平均温差乘修正系数倒推面积，结论却是面积不够。两边都说自己的表格没错，最后查出来是一边把壳程一程管程两程的修正系数查成了逆流。他想要一个服务，把两种方法放在同一套口径下算，并且能互相对账，谁有偏差一眼就能看出来。我答应帮他做。

服务要处理的流动布置：逆流、顺流、一壳程偶数管程的管壳式、以及两种单程叉流（两股流体都不混合；最小热容流体混合而另一股不混合，或反过来）。相变侧（冷凝或沸腾）按热容流率无穷大处理，此时热容流率比为零。

核算方向（已知换热器求出口）：给定两侧质量流量、定压比热、进口温度，以及总传热系数与面积（或直接给 UA），服务求出热负荷、两侧出口温度、效能、传热单元数、热容流率比。设计方向（已知工况求换热器）：给定两侧进口温度与一侧目标出口温度，求所需 UA 与面积；所需效能超过该布置在这一热容流率比下能达到的极限时，要明确报告不可实现以及极限值，不能返回 NaN 或负面积。两种方向都要同时给出用对数平均温差法得到的结果：对数平均温差、修正系数 F、以及 F·UA·LMTD 算出的热负荷。管壳式布置下 F 低于 0.75 时给出温度交叉风险警告；两端温差相等时，对数平均温差要取极限值，不许除以零。

对账功能：调用方可以提交一台换热器的现场实测数据（两侧流量、四个端点温度），服务先检查两侧热平衡偏差，再用参数档里登记的 UA 分别按两种方法预测出口温度，与实测对比，给出每一项偏差；还要由实测温度反推当前实际 UA，与登记值相比算出污垢热阻的增量。热平衡偏差超过调用方给定百分比时，结果标为“实测不可信”，但其余数值照常给出。

换热器参数档：每台换热器登记名称、布置形式、面积、设计总传热系数和备注，存成数据目录里的 JSON 文件，服务重启后仍在；计算时可以点名一台，也可以临时给参数。多个请求同时修改和读取参数档时，文件内容不能损坏。

我希望测试里能看到这些关系成立：任何布置下，核算得到的热负荷与 F·UA·LMTD 一致（相对误差小于 1e−9）；热侧放热等于冷侧吸热；核算得到的出口温度送进设计方向，求回来的 UA 与原值一致；热容流率比为零时，所有布置的效能都等于 1 − e^(−NTU)；热容流率比为 1 的逆流，效能等于 NTU/(1+NTU)；同一 NTU 和热容流率比下，逆流效能不低于其它任何布置，顺流效能不高于其它布置；顺流的效能永远不超过 1/(1+Cr)；交换两股流体的冷热角色（温度按相反方向对应）不改变热负荷大小。

非法输入返回带字段名的错误：流量、比热、面积、传热系数非正；热侧进口温度不高于冷侧进口温度；目标出口温度越过对侧进口温度；管壳式管程数不是正偶数；实测温度违反冷热方向（冷侧出口高于热侧进口）。

技术栈：Node.js 20 + TypeScript，Web 框架用 Express；不用数据库。代码拆成：流动布置的效能关系、对数平均温差与修正系数、核算与设计求解、实测对账与污垢反推、参数档读写、输入校验、路由。测试用 Jest 或 Vitest，上面的关系逐条有用例，每种非法输入至少一例。镜像基于 node:20-slim，TypeScript 在构建阶段编译，运行阶段只带编译产物和生产依赖，数据目录挂卷；docker build 完直接 docker run 即可对外服务。只做 HTTP 接口，不要前端页面。
